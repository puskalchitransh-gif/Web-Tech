Introduction to Web Services

Not Attempted

According to the W3C, a Web Service is a software system designed to support interoperable machine-to-machine interaction over a network. It provides a formal interface described in a machine-processable format (specifically WSDL). Other systems interact with the web service using SOAP or REST messages conveyed via HTTP with an XML or JSON serialization in conjunction with other web-related standards.

1. Core Characteristics of Web Services

  • Platform & Language Independence: A web service authored in Java on Linux can be consumed seamlessly by a C# .NET application on Windows or a Python script on macOS.
  • Loose Coupling: Consumers and providers are decoupled in time and implementation. The client only needs the contract (WSDL or OpenAPI), not the server's internal object model.
  • Standardized Communication Protocols: Employs ubiquitous Internet protocols (HTTP, HTTPS, SMTP) that navigate corporate firewalls without requiring custom port configurations.
  • Composability: Discrete granular web services can be aggregated into complex business workflows using orchestration languages (e.g., WS-BPEL).

2. Architectural Paradigms: SOAP vs REST

Criteria SOAP (Simple Object Access Protocol) REST (Representational State Transfer)
Nature Strict protocol with formal specifications Architectural style using standard HTTP semantics
Data Format Exclusively XML (SOAP Envelope) Flexible (JSON, XML, HTML, plain text)
Interface Contract Mandatory formal contract (WSDL) Optional / semi-formal (OpenAPI / Swagger)
Transport HTTP, HTTPS, SMTP, JMS, TCP Exclusively HTTP / HTTPS
Enterprise Features Native WS-Security, WS-ReliableMessaging, WS-AtomicTransaction Rely on underlying transport (TLS/HTTPS, OAuth 2.0)

UDDI (Universal Description, Discovery and Integration)

Not Attempted

UDDI is an OASIS standard and XML-based registry that enables businesses to publish service listings, discover partner web services, and define how services interact over the Internet. It functions conceptually as the "Telephone Directory" of Service-Oriented Architecture.

1. The Three Registry Information Categories

  • White Pages: Business name, textual description, administrative contacts, phone numbers, and unique corporate identifiers (e.g., Dun & Bradstreet D-U-N-S numbers, tax identification codes).
  • Yellow Pages: Categorization of businesses and services using standard industrial taxonomy classification schemes, such as NAICS (North American Industry Classification System) or UNSPSC (United Nations Standard Products and Services Code).
  • Green Pages: In-depth technical specifications describing how to invoke the service, including network endpoint URLs, communication protocols, and references to formal WSDL interfaces.

2. Core UDDI XML Data Structures

Data Entity XML Tag Description & Role
Business Entity <businessEntity> Represents the service provider company; contains White Pages and Yellow Pages information.
Business Service <businessService> Represents a logical group of web services offered by the business entity.
Binding Template <bindingTemplate> Contains technical endpoint address (Green Pages) where the service is hosted.
Technical Model <tModel> The fingerprint technical specification or interface contract (points to WSDL).

SOAP (Simple Object Access Protocol)

Not Attempted

SOAP is a W3C-standard XML-based messaging protocol for exchanging structured data in decentralized, distributed environments. A SOAP message is fundamentally an XML document consisting of distinct structural layers.

1. Structural Anatomy of a SOAP Message

  1. SOAP Envelope (<soap:Envelope>): The mandatory root element that identifies the XML document as a SOAP message and defines namespace prefixes.
  2. SOAP Header (<soap:Header>): An optional element containing metadata and cross-cutting enterprise concerns (authentication tokens, digital signatures, transaction identifiers, routing instructions).
    • mustUnderstand="1": A critical attribute. If a recipient or intermediary node cannot process a header with this attribute set to 1, it MUST reject the message and generate a SOAP Fault.
  3. SOAP Body (<soap:Body>): The mandatory element containing the actual application request payload or response data.
  4. SOAP Fault (<soap:Fault>): A standardized sub-element located inside the Body used exclusively for returning error status and diagnostic information (contains faultcode, faultstring, faultactor, and detail).
Standard SOAP 1.2 Request Envelope XML / SOAP 
<?xml version="1.0" encoding="UTF-8"?>
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope"
               xmlns:wt="http://quantumuniversity.edu/webtech">
  <soap:Header>
    <wt:AuthToken soap:mustUnderstand="true">
      eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
    </wt:AuthToken>
  </soap:Header>
  <soap:Body>
    <wt:GetStudentDetailsRequest>
      <wt:RollNumber>2101034</wt:RollNumber>
      <wt:Semester>5</wt:Semester>
    </wt:GetStudentDetailsRequest>
  </soap:Body>
</soap:Envelope>

WSDL (Web Services Description Language)

Not Attempted

WSDL is an XML format for describing network services as a set of endpoints operating on messages containing either document-oriented or procedure-oriented information. It serves as the programmatic contract between client and server.

1. Core Elements of a WSDL 1.1 Document

  • <types>: Container for data type definitions using XML Schema (XSD) syntax.
  • <message>: Abstract, typed definition of the data being communicated (each input and output parameter is defined as a message part).
  • <portType>: An abstract set of operations supported by one or more endpoints. An operation corresponds to a method/function in standard OOP (e.g., getGrade).
  • <binding>: Concrete protocol and data format specifications for a particular portType (e.g., binding the abstract operations to SOAP 1.2 over HTTP with style="document").
  • <port>: Defines an individual physical network address (URL) for a binding.
  • <service>: A collection of related ports.
High-Level WSDL 1.1 Hierarchy WSDL Architecture 
<definitions name="CourseService" ...>
  <types> ... XSD Schemas ... </types>
  <message name="GetStudentRequest"> ... </message>
  <message name="GetStudentResponse"> ... </message>
  
  <portType name="CoursePortType">
    <operation name="getStudent">
      <input message="tns:GetStudentRequest" />
      <output message="tns:GetStudentResponse" />
    </operation>
  </portType>
  
  <binding name="CourseSoapBinding" type="tns:CoursePortType">
    <soap:binding transport="http://schemas.xmlsoap.org/soap/http" style="document" />
    ...
  </binding>
  
  <service name="CourseService">
    <port name="CoursePort" binding="tns:CourseSoapBinding">
      <soap:address location="https://api.quantumuniversity.edu/ws/course" />
    </port>
  </service>
</definitions>

Web Service Architecture

Not Attempted

The foundational architecture of Web Services is built upon the classic SOA Service Triangle comprising three distinct roles and three fundamental operations.

1. The Three Primary Architectural Roles

  • Service Provider: The platform or organization that designs, develops, hosts, and operates the web service. It authors the WSDL description and registers its availability with a registry.
  • Service Requester (Consumer): The application client requiring specific business functionality. It queries the registry, extracts the WSDL contract, generates a client stub proxy, and invokes the service.
  • Service Registry: The searchable central directory (such as UDDI) where service providers publish service metadata and where consumers query for needed capabilities.

2. The Three Fundamental Operations (Publish, Find, Bind)

  1. Publish: The Service Provider transmits its business profile and WSDL technical binding to the Service Registry using the UDDI Publication API.
  2. Find: The Service Requester executes a search query against the Service Registry (using UDDI Inquiry API) to locate active services that satisfy its functional requirements.
  3. Bind: After obtaining the WSDL file from the registry, the Service Requester parses the endpoint address and binding specifics, binds directly to the Service Provider, and exchanges SOAP messages over HTTP at runtime.
💡
Enterprise Service Bus (ESB) & Orchestration In modern enterprise SOA, an Enterprise Service Bus (ESB) acts as an intelligent intermediary providing protocol transformation, message routing, and security. Enterprise workflows are automated using Orchestration (WS-BPEL, where a central coordinator controls service execution) or Choreography (peer-to-peer decentralized collaboration).

Developing and Deploying Web Services

Not Attempted

In enterprise environments, web services are developed using standardized platforms such as the Java EE / Jakarta EE framework through JAX-WS (Java API for XML-Based Web Services) and JAX-RS (Java API for RESTful Web Services).

1. Code-First vs Contract-First Development

  • Code-First (Bottom-Up): The developer writes Java / C# service implementation classes first and annotates them. The framework's tooling (e.g., wsgen) automatically generates the WSDL file and XML schemas at compile time or deployment. Fast and convenient, but can produce fragile XML schemas tied to language internals.
  • Contract-First (Top-Down): The developer first designs the XML Schema (XSD) and WSDL contract independently. Tools like wsimport (in Java) or svcutil (in .NET) then generate the strongly typed Java service skeletons and client proxies. Considered best practice in enterprise distributed computing.
JAX-WS Annotated Service Endpoint Implementation (SEI) Java JAX-WS 
package edu.quantumuniversity.webtech;

import javax.jws.WebService;
import javax.jws.WebMethod;
import javax.jws.WebParam;
import javax.jws.soap.SOAPBinding;

@WebService(name = "GradeCalculatorService",
            targetNamespace = "http://quantumuniversity.edu/grades")
@SOAPBinding(style = SOAPBinding.Style.DOCUMENT)
public class GradeCalculatorService {

    @WebMethod(operationName = "calculateSGPA")
    public double calculateSGPA(
        @WebParam(name = "theoryMarks") int theoryMarks,
        @WebParam(name = "practicalMarks") int practicalMarks) {
        
        return (theoryMarks * 0.7) + (practicalMarks * 0.3);
    }
}

Ajax – Improving Web Page Performance

Not Attempted

In February 2005, Jesse James Garrett of Adaptive Path coined the acronym Ajax (Asynchronous JavaScript and XML). Prior to Ajax, web interactions adhered to a synchronous "Click → Wait → Full Page Refresh" lifecycle: submitting a single form field required the browser to blank the screen, discard the entire DOM, download a complete new HTML page, re-parse styles, and re-execute all scripts.

1. How Ajax Revolutionized Web Performance

  • Partial Page Updates: Only the specific section of the UI requiring updated data is re-rendered (e.g., updating a score counter without reloading the video playing beside it).
  • Bandwidth Reduction: Instead of transmitting 500 KB of repeated HTML boilerplate, headers, and navigation menus, the server transmits only a tiny 2 KB JSON payload representing the raw data values.
  • Non-Blocking User Experience: Because data fetching runs asynchronously in the background, users can continue typing, scrolling, or interacting with the page with zero UI freezes.

2. Performance Engineering Strategies with Ajax

  • Debouncing: Postponing execution of an asynchronous search request until a specified pause in keystrokes (e.g., waiting 300ms after the student stops typing).
  • Throttling: Enforcing a maximum limit on how frequently an asynchronous call fires during rapid continuous events (such as window resizing or page scrolling).
  • Optimistic UI: Instantly updating the local client UI immediately upon user action (e.g., toggling a "completed" checkbox) before the network response returns, rolling back only if an error occurs.
  • Request Cancellation: Using AbortController to cancel outdated, pending background HTTP requests when the user rapidly changes views or filters.

Programming in Ajax (XMLHttpRequest & Fetch)

Not Attempted

Modern web development implements Ajax using two primary client-side APIs: the traditional XMLHttpRequest object and the modern Promise-based Fetch API with async/await.

1. Traditional XMLHttpRequest (XHR) Lifecycle

An XHR object transitions through 5 sequential readyState values:

  • 0: UNSENT — Client created; open() not yet called.
  • 1: OPENED — open() called; headers can be set.
  • 2: HEADERS_RECEIVED — send() called; status and headers available.
  • 3: LOADING — Downloading response payload; responseText holds partial data.
  • 4: DONE — Operation complete.
XMLHttpRequest vs Modern Fetch with async/await JavaScript 
// 1. Classic XMLHttpRequest Implementation
function loadSyllabusXHR() {
  const xhr = new XMLHttpRequest();
  xhr.open("GET", "/api/syllabus/unit3", true);
  xhr.setRequestHeader("Accept", "application/json");

  xhr.onreadystatechange = function() {
    if (xhr.readyState === 4) {
      if (xhr.status === 200) {
        const data = JSON.parse(xhr.responseText);
        console.log("XHR Success:", data);
      } else {
        console.error("XHR Error:", xhr.statusText);
      }
    }
  };
  xhr.send();
}

// 2. Modern Fetch API with async/await & AbortController
async function loadSyllabusFetch(timeoutMs = 5000) {
  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), timeoutMs);

  try {
    const response = await fetch("/api/syllabus/unit3", {
      method: "GET",
      headers: { "Accept": "application/json" },
      signal: controller.signal
    });

    if (!response.ok) {
      throw new Error(`HTTP Error: ${response.status}`);
    }

    const data = await response.json();
    console.log("Fetch Success:", data);
    return data;
  } catch (err) {
    if (err.name === 'AbortError') {
      console.warn("Request timed out!");
    } else {
      console.error("Fetch Failure:", err);
    }
  } finally {
    clearTimeout(timeoutId);
  }
}

CORBA (Common Object Request Broker Architecture)

Not Attempted

Defined in 1991 by the Object Management Group (OMG), CORBA is a standard architecture for distributed object computing. It allows applications written in different programming languages running on different operating systems across heterogeneous networks to invoke methods on remote objects as if they were local in-process objects (providing complete Location Transparency).

1. Architectural Building Blocks of CORBA

  • ORB (Object Request Broker): The foundational communications software bus. The ORB intercepts remote method invocations, marshals parameters into binary packets, locates the target object, and dispatches responses.
  • IDL (Interface Definition Language): A strictly typed, declarative language used to specify object interfaces, attributes, and method signatures independently of any target programming language.
  • Stub (Client Proxy): Generated by the IDL compiler; links into client code. When the client invokes a method, the stub marshals arguments and forwards the call to the ORB.
  • Skeleton (Server Adapter): Generated by the IDL compiler; receives the unmarshaled request from the ORB and calls the actual implementation method on the server servant object.
  • GIOP & IIOP: GIOP (General Inter-ORB Protocol) defines standard message formats; IIOP (Internet Inter-ORB Protocol) is the mapping of GIOP directly onto TCP/IP sockets.
  • IOR (Interoperable Object Reference): A stringified reference containing the remote host IP address, port number, and unique object key.
Sample CORBA OMG-IDL Interface Specification OMG IDL 
module QuantumUniversity {
  module WebTechnology {
    struct StudentRecord {
      string name;
      long rollNo;
      float sgpa;
    };

    interface StudentPortal {
      StudentRecord getStudent(in long rollNo);
      boolean updateMarks(in long rollNo, in float newMarks);
    };
  };
};

2. Why Web Services Replaced CORBA

Although CORBA delivered high execution speed, it struggled with massive enterprise adoption because:

  • Firewall Traversal: CORBA IIOP dynamically assigned non-standard TCP ports that corporate network firewalls routinely blocked. Web Services run over standard HTTP port 80 and HTTPS port 443.
  • Binary Complexity: CORBA utilized opaque, complex binary marshalling that made network packet debugging difficult compared to human-readable XML or JSON.
  • Tight Coupling: CORBA stubs and ORB vendor libraries introduced tight runtime coupling between client and server versions.
